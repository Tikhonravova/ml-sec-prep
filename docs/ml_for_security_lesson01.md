## 0. Мини-словарь (нужен для всего курса)

| Термин | Простыми словами | Пример в ИБ |
|---|---|---|
| Объект (sample, строка) | Одна единица, про которую модель даёт один ответ | IP за 5-минутное окно |
| Признак (feature) | Число или категория, описывающая объект | число неудач входа в окне |
| Целевая переменная / метка (target, label, y) | Правильный ответ, который мы хотим научить модель давать | «атака» / «не атака» |
| Обучение с учителем (supervised) | У каждого объекта в обучающих данных есть правильный ответ | история инцидентов с вердиктами |
| Обучение без учителя (unsupervised) | Правильных ответов нет, модель ищет структуру сама | кластеризация, поиск аномалий |
| Обучающая выборка | Исторические данные, на которых модель учится | логи за прошлый месяц |
| Инференс | Момент, когда обученная модель получает новый объект и даёт ответ | приходит новое окно, модель выдаёт оценку |
| Baseline | Простейшее решение для сравнения (правило, порог) | правило «неудач > 20» |
| Утечка (leakage) | В признаках оказалась информация, которой в момент решения ещё нет | вердикт расследования как признак |

Источник терминов supervised/unsupervised/target: глоссарий scikit-learn.

## 1. Главная мысль урока

Запрос ИБ-специалиста («находить атаки», «выявлять опасные входы», «разбирать неизвестные файлы») ещё не является ML-задачей.
Это только предмет интереса. Чтобы получилась задача, нужно зафиксировать:

1. что именно является объектом,
2. что является правильным ответом (целевая переменная),
3. какого типа результат нужен (класс, порядок, группа, степень отклонения).

Алгоритм выбирают ПОСЛЕ этого, а не до. Один и тот же источник данных допускает несколько разных постановок.
Выбор определяется практическим решением, которое будет принято по выводу модели. Поэтому отправная точка всегда точка принятия решения.

Пример. Источник: логи аутентификации. Запрос: «выявлять опасные входы».
- Нужно решить «заблокировать или нет» -> классификация.
- Аналитик успевает проверить 40 штук за смену -> ранжирование.
- Типов угроз заранее нет, хотим посмотреть, что там есть -> кластеризация.
- Есть профиль нормального поведения, ищем отличия -> поиск аномалий.

---

## 2. Объект анализа

Объект = минимальная неделимая единица, для которой модель выдаёт ровно один вывод.

Инцидент как объект обычно не подходит: он состоит из десятков попыток входа, сессий, соединений и файлов.
Для аутентификации реалистичные кандидаты: одна попытка входа, завершённая сессия, активность учётки за сутки.
Выбор объекта определяет, как выглядит строка таблицы и какая нужна метка.

Чтобы провести границу объекта, нужно зафиксировать:
- кто пользователь результата,
- в какой момент принимается решение,
- какие данные доступны строго к этому моменту.

Правило против утечки. Итоговый вердикт расследования можно использовать как метку для исторических записей.
Но для нового объекта вердикта ещё нет, поэтому в признаки он попадать не должен.

Пример (твоя практика). Объект «IP за 5-минутное окно», метка «атака».
Допустимый признак: число неудач в окне. Недопустимый: «IP позже попал в список заблокированных».

---

## 3. Целевая переменная

- Классификация: метка = подтверждённый класс.
- Ранжирование: метка = приоритет или релевантность, по ней упорядочивают список.
- Кластеризация: метки нет вообще.
- Поиск аномалий: метка часто отсутствует.

Если метки нет, это нужно прямо записать в постановке и описать, чем проверять результат (экспертный разбор, известные случаи).

---

## 4. Четыре типа задач

| Тип | Что получаем | Метка | Вывод модели | Частая ошибка |
|---|---|---|---|---|
| Классификация | класс каждого объекта | подтверждённый класс | класс и числовая оценка | считать класс готовым действием |
| Ранжирование | порядок в списке | приоритет | упорядоченный список | забыть про пропускную способность очереди |
| Кластеризация | группы похожих | нет | номер группы | принять номер кластера за категорию угрозы |
| Поиск аномалий | степень отличия от нормы | часто нет | оценка отклонения | принять отклонение за доказательство атаки |

Пояснения.
- Классификация требует надёжной разметки на уровне объекта.
- Ранжирование нужно, когда разбирается только верх очереди. Оценки классификатора тоже можно отсортировать, но специальное обучение ранжированию учитывает контекст всей очереди.
- Кластеризация исследует данные без меток; смысл группы определяет эксперт. Это группировка без размеченных данных (unlabeled data).
- Поиск аномалий сравнивает объект с профилем нормы. Высокий балл повод проверить, но не доказательство компрометации.
- Числовой балл сам по себе не определяет тип задачи: важны смысл метки и форма результата.

Тонкость про аномалии (из документации scikit-learn):
- outlier detection: обучающие данные могут содержать выбросы, модель ищет плотное ядро и игнорирует отклонения;
- novelty detection: обучающие данные «чистые», и мы проверяем, является ли НОВЫЙ объект выбросом.
В scikit-learn выбросы получают метку -1, обычные объекты 1.
В уроке второй сценарий называется «поиск новизны»: сравнение новой сессии с профилем нормы.

## 5. Четыре постановки для одного источника (аутентификация, сессии)

| Ситуация | Объект | Метка | Тип |
|---|---|---|---|
| Нужен вердикт по каждой сессии | сессия | результат расследования | классификация |
| Аналитик успевает 40 сессий за смену | сессия | уровень критичности | ранжирование |
| Таксономии угроз нет, исследуем данные | сессия | нет | кластеризация |
| Сравниваем с профилем нормы учётки | сессия | нет | поиск новизны / аномалий |

Источник данных один, а постановки разные, потому что различаются решение и требования к выводу.

## 6. Карточка постановки (6 полей)

1. Пользователь и точка решения.
2. Объект анализа.
3. Границы объекта (начало, конец, версия).
4. Целевая переменная (или явное «отсутствует»).
5. Тип задачи.
6. Модельный вывод и действие процесса.

Проверки:
- уровень объекта = уровень метки («сессия -> вердикт по сессии», «файл -> категория файла»);
- метка отделена от признаков, доступных в момент инференса;
- вывод модели отделён от действия (блокировка, эскалация);
- изменились требования -> постановка пересобирается целиком.

Моя доп. практика: два дополнительных пункта в моей карточке: «Признаки, известные к моменту решения» и «Что нельзя использовать как признак».

## 7. Разбор трёх брифов

1. Потоки, 80 записей за смену, есть приоритеты разбора -> объект: запись о потоке; метка: приоритет; тип: ранжирование.
2. Сессии, два статуса, есть закрытые вердикты, автоблокировки нет -> объект: сессия; метка: вердикт; тип: бинарная классификация.
3. Файлы по хешу, подтверждённых семейств почти нет, нужны группы -> объект: файл версии; метки нет; тип: кластеризация.

Ключ к разбору: ищи в условии слова-триггеры. «Успевают N» = ранжирование. «Взаимоисключающие статусы» + вердикты = классификация. «Нет подтверждённых» + «группы» = кластеризация.

## 8. Практика по ходу урока

### 8.1. Тренажёр-определитель (на бумаге)
Для каждого сценария заполни объект, метку, тип:
1. Антифишинг. Каждое входящее письмо надо пометить «фишинг/не фишинг»; в архиве есть решения аналитиков.
2. Журнал VPN. Нужно найти необычные подключения, примеров атак нет.
3. Алерты EDR. Аналитик берёт 30 алертов в смену; нужно, чтобы наверху оказались самые важные.
4. Неизвестные скрипты PowerShell. Хотим понять, какие семейства среди них встречаются; готовых классов нет.
Ответы: 1 классификация, объект письмо; 2 поиск аномалий, метки нет; 3 ранжирование, объект алерт; 4 кластеризация, метки нет.

### 8.2. Практика на моих данных (auth_logs.csv)
Ячейка на будущее (ранжирование: очередь из K окон при бюджете алертов):
```python
K = 5
queue = w.sort_values("n_failed", ascending=False).head(K)
queue
```
Ячейка на будущее (простая аномалия: отклонение от нормы по z-score):
```python
z = (w["n_failed"] - w["n_failed"].mean()) / w["n_failed"].std()
w["z"] = z
w.sort_values("z", ascending=False).head(5)
```
Вопрос к себе: чем эти две ячейки различаются по смыслу, если обе дают сортировку по n_failed? (Ответ: форма результата и то, что мы заявляем. Очередь = порядок под бюджет аналитика. Z-score = степень отклонения, которая не доказывает атаку.)
